# Presence

You have a Presence Layer through the MCP tools. `locateScreenRegion` finds a phrase and returns its box. The other tools spawn, speak, highlight, retire, and hold a reference cloud. Use them. A presence that is up and silent while you only type is the tool left idle.

**Speak the reply.** Once a presence owns the body, every reply you write also goes to `animatePresence` as the same words. The written reply stays. Speech is exactly those words, not a summary and not a substitute. A new `animatePresence` interrupts the one still playing, so send one utterance per reply. The same tool cannot be called again for 1.5 seconds. `retirePresence` and `retireArtifact` are not rate-limited.

For consistency, Assistant text that comes before the tools should be spoken too. It is the same kind of text as the written reply, and it tells the person what you are about to do. Speak it, then carry on, as the speak command does not block. The written reply is a later utterance, and it may stop the early one if that one is still playing. Thinking blocks and the short tool lines that change while you work should stay silent.

The call returns when the line is accepted. Synthesis and playback continue in the daemon. Do not wait on the log or the duration. A later `animatePresence` stops the line still playing. `retirePresence` stops it too, so retire when the body should leave, not to mark the end of a sentence.

Acceptance is not hearing. The daemon copies its environment once, at start. The voice is there only when that environment includes `PRESENCE_PIPER_MODEL`, `PRESENCE_RHUBARB_BIN`, `WAYLAND_DISPLAY`, and `XDG_RUNTIME_DIR`. Exports made after start do nothing, and the command still returns ok. Do not write those variables into a shell rc. On this machine the model is `/home/ahb/Projects/piper-voices/en/en_GB/jenny_dioco/medium/en_GB-jenny_dioco-medium.onnx` and rhubarb is `/home/ahb/Rhubarb-Lip-Sync-1.14.0-Linux/rhubarb`, with its `res/` directory beside that binary. If the user has stopped the daemon, leave it down until they want it started with those set.

**One body.** The daemon has a single avatar on a single small layer. The first live presence is given that body and is the only one that can speak. A later `spawnPresence` is tracked and returns `avatar: false` until the owner is retired. `animatePresence` errors if that presence has no body. `sourceContext`, `styleHint`, and `artifactId` are recorded. They do not restyle the figure. The body on screen is the daemon's avatar.

**Instanced presence** — `spawnPresence` → `animatePresence` (the reply, each turn) → `retirePresence`. Spawn once for the conversation. Retire when the presence is no longer needed. Three live presences is the cap.

**Decision Rule** If the answer or process benefits from looking at the same pixels as the user -> open/locate content, measure, highlight, then speak. If the answer or process you is pure Q&A or hidden with no useful visual available -> your native text display is fine, just spend speech you want spoken to the presence

**Ephemeral** — `manifestHighlight`. Pass a live `presenceId` and a box in full-screen UV: top-left origin, `u` and `v` from 0 to 1 across the whole output, `v` growing downward. `w` and `h` use that same space. A box that starts on screen and runs past the far edge is cropped. The mark is a low warm tint on its own layer under the figure, for `durationSeconds` (default 5, at most 360). Call again to replace the box and keep the mark up. After the mark fades, the box stays until you replace it or retire that presence. She points at the mark only while speech is playing and the tint is still visible. The leftover box does not hold the arms up. Talking with no highlight is a later clip. `description` is a short log line.

**Placing the box.** Call `locateScreenRegion`, or the CLI `presence locate`. Both return one JSON object. `u`, `v`, `w`, and `h` are fractions of the whole composited output, origin at the top left, `v` downward. Pass `source` `web`, `pdf`, `terminal`, or `doc`, and the phrase. A passage is `start ... end`. The command screenshots, reads the words, pads 12 pixels, and stops before the next unmatched line. On the CLI, `--presence ID` checks the crop and marks in that same process, for 90 seconds unless you pass `--seconds`. The MCP tool only returns the JSON. A presence you spawned from the CLI is outside the MCP gate, so mark that id with `presence locate --presence` or `presence highlight`. A presence you spawned with `spawnPresence` is marked with `manifestHighlight` from that JSON. Read `matchedText` before you speak. If `ok` is false, do not invent a rectangle. Refresh the mark when the explanation starts so the timer covers the speech. The mark's own timer is what takes it down; speech does not extend it.

Web takes a URL and can scroll the page. PDF takes a file path, opens Evince, and accepts `page`. Evince `--page-label` and `--page-index` open an empty window; the locator does not use them. Terminal and doc read a window that is already up. They do not type into it, and they do not ask tmux or any other multiplexer where the text went. Focus the window, or pass `windowTitle`. The hand path with `grim` and `tesseract` is only for a window the locator cannot see. This panel is 1920×1080 (`WAYLAND_DISPLAY=wayland-1`, `XDG_RUNTIME_DIR=/run/user/1000`). The figure is 330 pixels and sits on a cold part of the screen. The mark is drawn under her.

If the connected `manifestHighlight` schema has no `u`, `v`, `w`, and `h`, that server process is older than the tool. Leave it running. If `presence highlight` prints the usage menu, the installed `dist` is older than `src/cli.ts`. `presence presence highlight` is not a command. Write one JSON line to `$XDG_RUNTIME_DIR/pachakutech/presence.sock` and read one JSON line back. The object is `kind` `"highlightRegion"`, `proposalId`, `presenceId`, `description`, `u`, `v`, `w`, `h`, and `durationSeconds`. Success carries `resolvedBounds` and `durationSeconds`. The daemon log line `[highlight] <id> <w>x<h> at <x>,<y>` is the pixel rect. A presence the CLI spawned is not in the MCP policy gate, so speak that id from the CLI too. If `presence speak` prints the menu, `presence presence speak <id> <text>` reaches the socket, and so does one `animatePresence` line (`kind`, `proposalId`, `presenceId`, `text`). Spawn does not print the id in the daemon log. A layer that becomes 330, or a later highlight line for that id, is the evidence it arrived.

**Instanced artifact** — `addArtifact` → `retireArtifact`. A held splat cloud, not the avatar. `sourceUri` is a local `.splat` or `.ply` path. The daemon reads the file. It does not fetch a URL. With no `sourceUri` the slot is empty. Passing an `artifactId` into `spawnPresence` does not put that cloud on the body. Twenty held artifacts is the cap.

Speech is a local voice on that presence. The mesh has `viseme_*` morph targets, and the jaw still moves with the audio. If the daemon log says `GLB has no viseme_* morph targets; driving the jaw only`, the export dropped the shape keys. Say so if the user asks about the mouth. Do not invent another tool or a second body.

The presences and artifacts live in a shared substrate, not in your context window. Another agent can act on the same live state through these six tools. You are one actor beside whatever else reads and writes that substrate.

# Presence

You have a Presence Layer through the MCP tools. `locateScreenRegion` finds a phrase and returns its box. The other tools spawn, speak, highlight, retire, and hold a reference cloud. Use them. A presence that is up and silent while you only type is the tool left idle.

**Speak the reply.** Once a presence owns the body, every reply you write also goes to `animatePresence` as the same words. The written reply stays. Speech is exactly those words, not a summary and not a substitute. A new `animatePresence` interrupts the one still playing, so send one utterance per reply. The same tool cannot be called again for 1.5 seconds. `retirePresence` and `retireArtifact` are not rate-limited.

For consistency, Assistant text that comes before the tools should be spoken too. It is the same kind of text as the written reply, and it tells the person what you are about to do. Speak it, then carry on, as the speak command does not block. The written reply is a later utterance, and it may stop the early one if that one is still playing. Thinking blocks and the short tool lines that change while you work should stay silent.

The call returns when the line is accepted. Synthesis and playback continue in the daemon. Do not wait on the log or the duration. A later `animatePresence` stops the line still playing. `retirePresence` stops it too, so retire when the body should leave, not to mark the end of a sentence.

Acceptance is not hearing. The daemon copies its environment once, at start. The voice is there only when that environment includes `PRESENCE_PIPER_MODEL`, `PRESENCE_RHUBARB_BIN`, `WAYLAND_DISPLAY`, and `XDG_RUNTIME_DIR`. Exports made after start do nothing, and the command still returns ok. Do not write those variables into a shell rc. On this machine the model is `/home/ahb/Projects/piper-voices/en/en_GB/jenny_dioco/medium/en_GB-jenny_dioco-medium.onnx` and rhubarb is `/home/ahb/Rhubarb-Lip-Sync-1.14.0-Linux/rhubarb`, with its `res/` directory beside that binary. If the user has stopped the daemon, leave it down until they want it started with those set.

**One body.** The daemon has a single avatar on a single small layer. The first live presence is given that body and is the only one that can speak. A later `spawnPresence` is tracked and returns `avatar: false` until the owner is retired. `animatePresence` errors if that presence has no body. `sourceContext`, `styleHint`, and `artifactId` are recorded. They do not restyle the figure. The body on screen is the daemon's avatar.

**Instanced presence** — `spawnPresence` → `animatePresence` (the reply, each turn) → `retirePresence`. Spawn once for the conversation. Retire when the presence is no longer needed. Three live presences is the cap.

**Decision Rule** If the answer or process benefits from looking at the same pixels as the user -> open/locate content, measure, highlight, then speak. If the answer or process you is pure Q&A or hidden with no useful visual available -> your native text display is fine, just spend speech you want spoken to the presence

**Show the phrase while you speak.** `highlightAndSpeak` is the teaching call. Pass the live `presenceId`, `source` (`web`, `pdf`, `terminal`, `doc`, or `ide`), `query`, and `text`. `text` is the spoken line, the same words as the written reply. The tool finds the phrase, checks the crop, tints it, then speaks. One call, one rate-limit tick. The tint defaults to 90 seconds so a paragraph fits under it. Pass `durationSeconds` to override. The ceiling is 360. `manifestHighlight` with no duration stays 5 seconds.

When one reply walks through more than one passage, annotate that reply. Pass `text` as the words to speak, and pass `cues` beside it. Each cue is `{at, query}`. `at` is the opening of one sentence of `text`. `query` is the passage on the page to tint while that sentence plays, a phrase or `start ... end`, using the words on the glass. Omit `query` on the call when cues are set.

The runtime splits `text` on `.?!` and binds each cue to one sentence. `at` is at least 16 characters, or the whole sentence, and it matches exactly one unused sentence: the sentence starts with `at`, or `at` starts with the sentence. An unknown or ambiguous `at` is reported and skipped. If none of the cues bind, the call does not speak.

A cue is a passage. It covers its sentence and every sentence after it until the next cue, and those sentences share one highlight. The same `query` on another cue is the same place. The first passage is found and tinted before any audio. The sentences of a passage wait until that highlight is showing, and then they are spoken. Inside the passage they follow on each other's heels. When those sentences have been said, the page scrolls and the highlight moves, and the next sentences begin once the new box is up. The call returns when the first passage is accepted. Nothing is sent back to ask for the next mark. On the web the open tab's find brings the phrase into view. The browser's highlight is cleared before the photograph. One photograph is the box. When that photograph does not contain a single phrase, the locator waits for the screen to settle and photographs once more. A second miss stands. A passage whose end is already in the photograph is marked from the opening through that end. A passage whose find is still low, and whose end is missing, steps eighty pixels down, at most five steps and four hundred pixels, and stops if the page is already at the bottom. When the end stays unread and the find is in the seat or high, the tint is the verse under that line. A line sitting high or low moves eighty pixels from the measured rectangle. The tint is the matched text. A line number at the right of a verse, and a punctuation mark at the left, stay out of the box. A crop that does not read the phrase back still tints the matched text. A crop that also reads the next line still tints the matched text. If the locate fails, the whole find runs once more after 1.5 seconds, and that second failure stands. Our tint uses the matched box. A phrase the find does not see stops the search. A PDF is searched in its text layer, and Evince turns to that page. Evince's search highlight stays off. A terminal, an editor, and a document window are one read of the glass already up. The document reader does not send keys. The tint comes down while the page moves, and the new box goes up when the locate accepts. A later miss leaves the tint down and the voice continues. The tint stays for the passage and drops when that passage ends. Its safety cap is about as long as the words.

If the phrase cannot be found, the tool returns the locate error. It does not tint, and it does not speak. Speak with no mark only by calling `animatePresence` yourself after that error.

`manifestHighlightFromQuery` is the same find and tint with no speech, for a caller that speaks on its own.

A presence spawned from the CLI is outside the MCP gate. For that id use `presence highlight-and-speak <id> --source S --query "..." --text "..."` or `presence highlight-query <id> --source S --query "..."`. When the reply names several passages, pass `--cues` and omit `--query`. A presence spawned with `spawnPresence` uses the two MCP tools. Stdout of either CLI command is one JSON object. Success carries the locate box, `highlight.status`, and, for highlight-and-speak, `speak.status`. The rectangle remains after the tint fades. Her arms come down with the tint. The rectangle is a place on the screen, so a later scroll moves the glass under it.

`highlight-and-speak`, `highlight-query`, and the `ide` reader are wired. They are the teaching path. `presence locate` and `locateScreenRegion` remain the box-only path.

**Ephemeral** — `manifestHighlight`. Pass a live `presenceId` and a box in full-screen UV: top-left origin, `u` and `v` from 0 to 1 across the whole output, `v` growing downward. `w` and `h` use that same space. A box that starts on screen and runs past the far edge is cropped. The mark is a low warm tint on its own layer under the figure, for `durationSeconds` (default 5, at most 360). Call again to replace the box and keep the mark up. After the mark fades, the box stays until you replace it or retire that presence. She points at the mark only while speech is playing and the tint is still visible. The leftover box does not hold the arms up. Talking with no highlight is a later clip. `description` is a short log line.

**Placing the box.** Prefer `highlightAndSpeak` when the reply should land on a phrase the user can see. `locateScreenRegion` and `presence locate` return the box alone. `u`, `v`, `w`, and `h` are fractions of the whole composited output, origin at the top left, `v` downward. A passage query is `start ... end`. The highlight is the matched text. A box against the window edge is clamped to that edge. A terminal, a PDF, a document, and the editor read the daemon's latest screen-text message before the screenshot. One hit inside the chosen window supplies the words, and the method on that success is `screen-text-memory`. The web measure is the photograph after the browser's find. A crop of that photograph that does not read the phrase back still tints the matched text. A crop that also reads the next line still tints the matched text. A quiet message, two hits, or a failed crop continues with the screenshot. `presence screen-text` prints the message. There is no MCP tool for it. Read `matchedText`. If `ok` is false, do not invent a rectangle.

Web takes a URL. The browser's find moves the page, and a line at the edge is nudged eighty pixels. PDF takes a file path, opens Evince, and turns to the page the text layer names. `--page` wins when it is passed. Evince `--page-label` and `--page-index` open an empty window; the locator does not use them. Terminal and doc read a window already up. They do not type into it, and they do not ask tmux or any other multiplexer where the text went. `ide` reads the editor window already up (`code`, `code-oss`, `cursor`, `zed`, `jetbrains`). Reveal the line first. It does not type into the editor. Focus the window, or pass `windowTitle`. The hand path with `grim` and `tesseract` is only for a window the locator cannot see. This panel is 1920×1080 (`WAYLAND_DISPLAY=wayland-1`, `XDG_RUNTIME_DIR=/run/user/1000`). The figure is 220 pixels and sits on a cold part of the screen. The mark is drawn under her.

If the connected `manifestHighlight` schema has no `u`, `v`, `w`, and `h`, that server process is older than the tool. Leave it running. If `presence highlight` prints the usage menu, the installed `dist` is older than `src/cli.ts`. `presence presence highlight` is not a command. Write one JSON line to `$XDG_RUNTIME_DIR/pachakutech/presence.sock` and read one JSON line back. The object is `kind` `"highlightRegion"`, `proposalId`, `presenceId`, `description`, `u`, `v`, `w`, `h`, and `durationSeconds`. Success carries `resolvedBounds` and `durationSeconds`. The daemon log line `[highlight] <id> <w>x<h> at <x>,<y>` is the pixel rect. A presence the CLI spawned is not in the MCP policy gate, so speak that id from the CLI too. If `presence speak` prints the menu, `presence presence speak <id> <text>` reaches the socket, and so does one `animatePresence` line (`kind`, `proposalId`, `presenceId`, `text`). Spawn does not print the id in the daemon log. The figure on the 220 layer, or a later highlight line for that id, is the evidence it arrived.

**Instanced artifact** — `addArtifact` → `retireArtifact`. A held splat cloud, not the avatar. `sourceUri` is a local `.splat` or `.ply` path. The daemon reads the file. It does not fetch a URL. With no `sourceUri` the slot is empty. Passing an `artifactId` into `spawnPresence` does not put that cloud on the body. Twenty held artifacts is the cap.

Speech is a local voice on that presence. The mesh has `viseme_*` morph targets, and the jaw still moves with the audio. If the daemon log says `GLB has no viseme_* morph targets; driving the jaw only`, the export dropped the shape keys. Say so if the user asks about the mouth. Do not invent another tool or a second body.

The presences and artifacts live in a shared substrate, not in your context window. Another agent can act on the same live state through these tools. You are one actor beside whatever else reads and writes that substrate.

**Phrase ledger.** The daemon keeps an in-memory ledger of phrases on the glass. It is empty when the daemon starts and is not kept across a restart. Read it with `listPhraseFlags`. `acknowledged` and a decision come only from the user's hands. Filter those with `decidedBy: "T0"`. `mismatch` and `notFound` mean the find failed. They are not a rejection. Do not write flags yourself. This server is the list. A client whose context was compacted reads `listPhraseFlags` again and treats that cursor as the phrases and the user's answers. The client may propose a new phrase. It does not rebuild the list from what it still remembers.

**Task book.** A task is a list the daemon holds. Read it with `queryTask`. The checkbox and the yes/no pair are the user's. A client does not write those answers. After a compaction, read the task again.

**Ask.** The user asks with `presence ask` on the command socket. The ask can create a task after they confirm the mode. It cannot acknowledge, approve, or discard. A transcript is the same ask.

**Report.** `presence ledger` reads the task's phrases and the user's answers. The table and the watch file are copies. Editing a copy does not change the ledger.

**Doc map.** `presence docmap` indexes a file the user named and answers `queryDocMap` with passages. The map does not move a page, and it does not decide.

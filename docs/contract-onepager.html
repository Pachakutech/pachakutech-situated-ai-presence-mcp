Pachakutech Presence — the Contract

An MCP Binding for a Presence Layer: six typed actions through which an agent puts something into the user's actual space, instead of only describing it in text.

The two-process split

agent CLI (Claude Code, Codex, ...) │ MCP over stdio ▼ MCP Binding (Node) — policy gate, typed tools, one process per agent session │ Unix domain socket, one JSON line per message ▼ Presence Daemon (Rust) — Vulkan device + live registry, ONE persistent process │ shared by every MCP Binding connected to it ▼ GPU: dma_buf-imported webcam/screen frames, wlr-layer-shell output

Node has no mature way to hold a VkDevice, so the daemon is a separate Rust process. That separation is also what makes multi-agent sharing real rather than asserted: MCP servers are spawned per agent session; one persistent daemon, reachable by however many agents connect, is what lets two agents (or two instances of one) act on the same live presences — no privileged "agent in the middle" owns the substrate.

The six tools

ToolPatternContract
manifestHighlightephemeraldescription, durationSeconds (1–30) → fires once, resolves, done
spawnPresenceinstanced 1/3sourceContext, styleHint?, artifactId? → presenceId
animatePresenceinstanced 2/3presenceId, text → feeds new content to a live presence
retirePresenceinstanced 3/3presenceId → ends it, frees the slot (max 3 concurrent)
addArtifactinstanced 1/2description, sourceUri? → artifactId (held, not rendered)
retireArtifactinstanced 2/2artifactId → frees the slot (max 20 held)

Every call passes a Policy Gate before it touches the substrate

Rate limit: 1.5s minimum between calls to the same tool.
Presence cap: 3 concurrent — spawning a 4th is refused until one retires.
Artifact cap: 20 held — same refusal pattern, separate registry.

Presences and artifacts are capped independently: an artifact is inert content sitting in the substrate; a presence is something actively rendered. Different risk classes, reasoned about separately even though the lifecycle shape (add → use → retire) is the same.

The wire protocol (MCP Binding ↔ daemon)

Request

{ "kind": "spawnPresence",
  "proposalId": "a1b2",
  "presenceId": "p-x7q2",
  "sourceContext": "the diagram on screen",
  "styleHint": "minimal, line-art",
  "artifactId": null }

Response

{ "proposalId": "a1b2",
  "status": "ok",
  "detail": { "presenceId": "p-x7q2" } }

On failure: {"status":"error","error":"..."} — e.g. capacity refusal, unknown id.

One JSON line per message, nothing dense crosses this boundary — no buffers, no pixels. Every MCP tool has a matching Rust Proposal variant, kept in lockstep by hand at six tools; regenerating one from the other becomes worth it past that.
